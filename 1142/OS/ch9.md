# Memory
## 記憶體管理基礎與保護機制
- **基本概念**:在馮紐曼架構中，程式碼必須被載入主記憶體並置於行程 (process) 中才能執行 。CPU 只能直接存取暫存器 (registers) 與主記憶體
- **多重程式執行 (Multiprogramming)**:為了提升 CPU 的使用率，主記憶體中會同時存在多個行程
- **硬體位址保護**:為了確保操作正確，必須保護記憶體空間
    - 系統透過一對暫存器來定義合法的邏輯位址空間：Base register (基底暫存器) 與 Limit register (極限暫存器)
    - CPU 會檢查使用者模式下產生的每次記憶體存取，位址必須大於等於 Base，且小於 (Base + Limit)
    - 若發生越界（非法存取），硬體會產生 Trap 交給作業系統處理（addressing error）
## 位址綁定 Address Binding[極常考]
程式通常以二進位執行檔存在磁碟中，執行時需載入記憶體 。位址的綁定（將程式中的邏輯位址對應到實體記憶體位址）可以發生在三個不同的階段，這是考試的必考重點：
- **編譯時期 (Compile time)**:如果事先就知道程式將存放在記憶體的哪個位置，編譯器可以直接產生絕對程式碼 (Absolute code) 。若起始位置改變，則必須重新編譯
- **載入時期 (Load time)**:如果在編譯時期不知道記憶體位置，編譯器會產生可重定位程式碼 (Relocatable code) 。
- **執行時期 (Execution time)**:如果行程在執行期間可以在不同的記憶體區段間移動，位址綁定就會延遲到執行時期才進行 。這需要特殊硬體的支援（如 base 和 limit 暫存器）
## 邏輯位址 vs. 實體位址[極常考]
區分這兩種位址是正確管理記憶體的核心概念
- **邏輯位址 (Logical Address)**:由 CPU 所產生的位址，又稱為虛擬位址 (Virtual address) 。使用者程式只會接觸到邏輯位址，永遠看不到真正的實體位址。
- **實體位址 (Physical Address)**:記憶體硬體實際看到的位址。
- **綁定時機的差異**:在「編譯時期」與「載入時期」綁定時，邏輯位址與實體位址是相同的 ；但在「執行時期」綁定時，兩者就會不同
- **記憶體管理單元 (MMU, Memory-Management Unit)：**
    - 負責在執行時期將虛擬位址映射 (map) 到實體位址的硬體裝置 。
    - **運作方式**:在簡單的機制中，MMU 會將 Relocation register (重定位暫存器) 的值，加上使用者行程產生的邏輯位址，轉換成送往記憶體的實體位址 。
## 動態載入與重疊技術
- **動態載入 (Dynamic Loading)：**
    - 副程式 (routine) 直到被呼叫時才會被載入記憶體中 。
    - **優點**:提升記憶體空間利用率，未使用的副程式永遠不會被載入 。這對於處理極少發生的狀況（但需要大量程式碼）特別有用
    - **特色**:不需要作業系統的特別支援，是由程式設計本身來實作
- **重疊 (Overlay)**:
    - 這是一種程式設計技巧，用來執行「比主記憶體容量還要大」的程式
    - 程式設計師將程式切分成多個區塊（稱為 overlays 或 links）。
    - 沒有相依性的區塊可以共用同一塊記憶體空間（稱為 Overlay region）。
## 靜態連結 vs. 動態連結 [常考比較題]
- **靜態連結 (Static Linking)**:在編譯與載入階段，系統函式庫與程式碼會被 Loader 直接合併成一個完整的二進位程式影像檔 。缺點是檔案較大且浪費記憶體空間。
- **動態連結 (Dynamic Linking)**:
    - 將連結的動作延遲到「執行時期 (Execution time)」才進行 。
    - **Stub (存根)**:程式中會使用一小段稱為 stub 的程式碼，用來定位常駐在記憶體中的函式庫副程式 。執行時，stub 會將自己替換為該副程式的實際位址並執行。
    - 作業系統會檢查該副程式是否已在記憶體中，若無則將其加入位址空間。
    - **應用場景**:特別適用於系統函式庫 (System libraries / Shared libraries)，以及修補系統函式庫 (Patching) 。
## 連續記憶體配置 (Contiguous Allocation)
- 早期的方法會將記憶體分為作業系統 (OS) 區與使用者行程區 。
- **變動分割 (Variable Partition)**:OS 會在記憶體中維護各種大小的可用區塊（Hole） 。當行程到達時，會尋找夠大的可用區塊配置給它 。
- **記憶體配置策略 (Allocation Strategies) [常考重點]**:
    - **First-fit (首次適應)**:從頭搜尋，分配第一個夠大的區塊 。
    - **Best-fit (最佳適應)**:搜尋整個列表，分配「夠大且最小」的區塊。這會產生最小的剩餘可用空間 。
    - **Worst-fit (最差適應)**:分配「最大」的區塊。這會產生最大的剩餘可用空間 。
- **碎裂問題 (Fragmentation) [必考名詞解釋] ：**
    - **外部碎裂 (External-Fragmentation):** 記憶體中總剩餘空間足夠，但因為空間不連續而無法分配給行程 。可透過壓縮 (Compaction) 解決 。
    - **內部碎裂 (Internal Fragmentation)**:分配給行程的記憶體比實際請求的稍微大一些，這多出來在區塊內部的空間無法被其他行程使用 。
## 分段 (Segmentation)
- **概念**:這是一種符合「使用者視角」的記憶體管理方式 。程式被視為多個「段落」（如主程式、副程式、堆疊、陣列等）的集合 。
- **邏輯位址結構**:由兩個部分組成：<segment-number, offset>
- **分段表 (Segment table)**:用來將邏輯位址轉為實體位址，每個條目包含：
    - **base (基底)**: 該段落在實體記憶體的起始位址 。
    - **limit (極限)**:該段落的長度 。硬體會檢查 offset 是否小於 limit 來防止越界存取 。
## 分頁 (Paging)
- **概念**:為了解決外部碎裂與避免壓縮，分頁技術將實體記憶體切割為固定大小的 Frames (頁框) ，並將邏輯記憶體切割為相同大小的 Pages (分頁) 。
- **優缺點**:分頁可以避免外部碎裂，但會產生內部碎裂 。因為行程大小通常不會剛好是分頁大小的整數倍，最後一個分頁通常無法填滿 。
- **位址轉換 (Address Translation) [常考概念]**:
    - 邏輯位址被劃分為：Page number ($p$) 與 Page offset ($d$) 。
    - $p$ 用來作為索引查詢分頁表 (Page table)，找出對應的 Frame 實體基底位址 。
    - Frame 基底位址加上 offset ($d$) 即為實體位址 。
## 硬體支援與 TLB 加速
- **問題**:若將分頁表存放在主記憶體，每次存取資料或指令都需要「兩次」記憶體存取（第一次查分頁表，第二次拿資料），效能會很差 。
- **TLB (Translation Look-aside Buffers) [極常考硬體機制]**:
    - **生活化比較TLB跟分頁表放在主記憶體**
        - 主記憶體的分頁表」是一本放在圖書館櫃檯的厚重實體電話簿，而「TLB」是你大腦裡的常用聯絡人記憶。如果你每次打電話都要先跑去圖書館翻厚重的電話簿查號碼（第一次存取），查到後才能撥打並與對方通話（第二次存取），會非常沒效率。而 TLB 就像是你記住了最近常打的幾個號碼，要打的時候大腦「瞬間」就能回想起來並直接撥出，直接省去了翻書的時間。
    - TLB 是一種具備平行搜尋能力的高速快取，用來儲存最近使用過的分頁表條目 。
    - **運作流程**:若 CPU 產生的 Page number 在 TLB 中找到 (TLB hit)，就能直接取得 Frame number；若沒找到 (TLB miss)，則必須去主記憶體查分頁表，並將結果載入 TLB 。
- **有效存取時間 (Effective Access Time, EAT) [必考計算題]**:
    - 給定 TLB 搜尋時間 ($\epsilon$)、記憶體存取時間 (通常設為 100ns) 以及 Hit ratio ($\alpha$) 。
    - 公式:$EAT=(1+\epsilon)\alpha+(2+\epsilon)(1-\alpha)=2+\epsilon-\alpha$ 。考試常會要求代入數字計算平均存取時間。
## 記憶體保護與共用
- **保護機制**:每個頁框會搭配一個 Valid-invalid bit (有效/無效位元) 。若設為 Valid，代表該分頁位於行程的合法邏輯空間；若為 Invalid，表示非法存取，會觸發 trap 交給作業系統處理 。
- **共用分頁 (Shared Pages)**:
    - 唯讀且可重入的程式碼 (Reentrant code) 可以在多個行程之間共用，藉此節省記憶體空間 。
    - **限制**:這些共用的程式碼必須在所有參與行程的邏輯位址空間中，出現在完全相同的位置 。而私有資料 (Private data) 則可以放在邏輯空間的任何地方 。
## 分頁表結構的優化 (Structure of the Page Table)
- **問題背景**: 如果系統直接使用單層的陣列來當作分頁表，在位址空間很大時（例如 32 位元系統配上 4KB 的 Page size），分頁表本身會龐大到佔用極多的記憶體（高達 4MB），非常浪費空間 。
- **階層式分頁表 (Hierarchical Page Tables)** [常考計算題]:
    - 解決方法是「將分頁表本身再進行分頁
    - 兩層式分頁 (Two-level paging)：以 32 位元系統為例，邏輯位址會被拆成三部分：外層分頁號碼 ($p_1$)、內層分頁號碼 ($p_2$)，以及分頁位移量 ($d$) 
    - 考點：考試非常喜歡給定「系統位元數」與「Page size」，要你推算 $p_1$、$p_2$ 和 $d$ 各佔多少位元，或是計算分頁表的大小。
- **64 位元系統的挑戰**：即使採用兩層或三層分頁，外層分頁表依然過於龐大，且會導致 CPU 為了拿一筆資料需要存取好幾次記憶體，效能極差 。
## 進階分頁表技術
為了應付 64 位元龐大的位址空間，發展出了以下兩種分頁表：
- **雜湊分頁表 (Hashed Page Tables)：**
    - 將虛擬分頁號碼 (Virtual page number) 透過 Hash function 對應到分頁表中 。
    - 發生碰撞時，使用鏈結串列 (Chain) 來存放並比對正確的實體頁框 。
- **反轉分頁表 (Inverted Page Tables) [常考觀念與優缺點]**
    - **核心概念**:打破傳統「每個行程都有自己專屬分頁表」的做法。變成整個系統只有一張分頁表，而且是「每一個實體記憶體的 Page 佔用一個條目」 。條目中會記錄目前是哪個行程 (PID) 的哪個虛擬位址佔用了該空間 。
    - **優點**:極大地減少了儲存分頁表所需的記憶體空間 。
    - **缺點 1**: 搜尋時間變長，因為必須用虛擬位址去整張表裡面搜尋（通常會搭配 Hash Table 與 TLB 來加速） 
    - **缺點 2 (常考)**: 很難實作「共用記憶體 (Shared Memory)」。因為同一個實體位址的條目中，同一時間只能記錄一個虛擬位址的對應，其他行程若要共用會引發 Page fault 並取代原有的對應 。
## 置換機制 (Swapping)
- **基本概念**: 當主記憶體快滿時，作業系統會把暫時用不到的行程移出 (Swap out) 到磁碟 (Backing store) 中，把空間讓給需要執行的行程；等到該行程要執行時再把它移回 (Swap in) 記憶體 。
- **效能瓶頸**: Swapping 會導致 Context Switch 的時間變得非常高，因為大部分的時間都花在磁碟與記憶體之間的資料傳輸時間 (Transfer time) 上 。
- **限制**: 如果一個行程正在進行 I/O 動作（例如等待硬碟讀取），絕對不能把它 Swap out，否則 I/O 資料可能會寫錯行程的記憶體位置 。
- **現代 OS 與行動裝置的差異**:
    - **現代 OS**: 已經不使用標準的 Swapping，而是採用修改過的版本，只有在「可用記憶體極度不足」時才會啟動置換 。
    - **行動裝置 (Mobile Systems)**: iOS 與 Android 通常不支援傳統的 Swapping
        - **原因**: 行動裝置採用快閃記憶體 (Flash memory)，其寫入次數 (Write cycles) 壽命有限，且頻寬吞吐量不如傳統磁碟 。
        - **解法**: iOS 會要求 APP 主動釋放記憶體，若不從則直接終止 (Terminate) 該 APP 。Android 則會在終止 APP 前，將其應用程式狀態快速寫入快閃記憶體，以便日後快速重啟 。
