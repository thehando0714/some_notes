# Deadlock
## 死結問題的定義(The Deadlock Problem)
- 在多道程式設計(multiprogramming)環境中，多個進程/執行緒可能會競爭有限數量的資源。
- 當一個進程請求資源時，如果該資源當下不可用，進程會進入等待狀態。
- 有時候，一個處於等待狀態的進程可能永遠無法改變其狀態。這是因為他所請求的資源被其他同樣在等待的進程所持有
- 這種所有進程都在互相等待的僵局情況就稱為死結。
## 系統模型(system model)
- 系統由多種資源類型組成，例如$R1$,$R2$....。這些資源可能包含CPU週期，記憶體空間以及I/O設備等。
- 每種資源類型$Ri$可能具有$Wi$個實例(instance)(實例就是這份資源Ri有幾個)。
- 每個進程使用資源的標準步驟為:
    1. **請求(request)**:執行緒向系統請求資源。
    2. **使用(use)**:執行緒對取得的資源進行操作。
    3. **釋放(release)**:執行緒將資源釋放歸還系統。
## 死結發生的四個必要條件(necessary condition)
死結的發生必須同時滿足以下四個條件:
1. **互斥(mutual exclusion)**:一次只能有一個執行緒使用某個資源。
2. **持有並等待(hold and wait)**:一個已經持有至少一個資源的執行緒，正在等待獲取由其他執行緒所持有的額外資源。
3. **不可搶占(no preemption)**:資源只能由持有它的執行緒在完成任務後{自願}釋放，無法被系統強制剝奪。
4. **循環等待(circular wait)**:存在一組等待中的執行緒{T0,T1....}，其中T0正在等待由T1持有的資源，T1等待T2持有的資源，以此類推，直到Tn正在等待T0持有的資源，形成一個循環。
## 資源分配圖(Resource-Allocation Graph)
- 這是一種用來描述系統資源型態的圖形，包含頂點集合V與邊緣集合E。
- 基本事實:
    - 若每種資源只有一個實例，則必定發生死結。
    - 若每種資源有多個實例，則可能發生死結(但不一定)。
##  處理死結的方法 (Handling Methods)
一般來說，處理死結有以下幾種主要方式 ：
- 使用協定來預防 (Prevention) 或避免 (Avoidance) 死結，確保系統永遠不會進入死結狀態
- 允許系統進入死結狀態，然後對其進行檢測並恢復 (Recover) 。
- 完全忽略這個問題，假裝系統中從未發生過死結
## 死結預防機制 (Deadlock Prevention)
要預防死結，核心思想是確保前面提到的「四個必要條件」中，至少有一個無法成立 ：
- **打破互斥**:通常無法透過這個條件預防死結，因為某些資源(如印表機)本質上就是不可共享的，必須互斥存取。
- **打破持有並等待**:必須保證進程在請求資源時，不持有任何其他資源。作法包含要求執行緒在執行前一次請求資源，或是在請求額外資源前釋放目前擁有的 資源。
    - **缺點**:資源利用率低，且可能導致進程飢餓(starvation)。
- **打破不可搶佔**:如果一個持有資源的執行緒請求新資源但無法立即獲得，系統會搶佔他目前持有的所有資源。被搶佔的資源會加入該執行緒的等待清單中，直到她能同時獲得舊資源與新資源才會重新啟動。
- **打破循環等待**:對所有資源類型實施完全排序(total ordering)，並要求每個進程只能按照遞增的順序請求資源，藉此打破循環的可能。**但要注意**，即使建立了鎖的順序，如果是動態獲取鎖，**依舊無法絕對保證能預防死結**。
## 安全狀態(safe state)與不安全狀態(unsafe state)
在分配資源前，系統會先評估分配後的狀態是否「安全」。
- **安全狀態**:如果系統能夠找到一個所有執行緒的{安全序列(safe sequence)}，就代表是安全的。這意味著每個執行緒Ti剩餘需要的資源，都可以透過{目前系統可用資源}加上{排在他前面的執行緒執行完畢後釋放的資源}來滿足。
- **不安全狀態**:如果找不到一個這樣的序列系統就處於不安全狀態。
- 考點
    1. 安全狀態絕對不會發生死結。
    2. 不安全狀態 不一定代表已經死結，他只代表有可能發生
## 多重實例資源：銀行家演算法 (Banker's Algorithm)
去看課堂小考或是直接看講義分為**安全性演算法** (Safety Algorithm)：用來檢查當前狀態是否安全跟**資源請求演算法** (Resource-Request Algorithm)
- **安全性演算法 (Safety Algorithm)**：用來檢查當前狀態是否安全 。  
    - 尋找一個尚未完成 (Finish == false) 且其需求可以被目前可用資源滿足的進程 (Need <= Work) 。  
    - 如果有，就假設它能順利完工並釋放資源，將它的 Allocation 加回 Work 中 (Work = Work + Allocation)，並標記為完成 
    - 一直重複，如果最後所有進程都能被標記為 true，系統就是安全的
- 資源請求演算法 (Resource-Request Algorithm)：當某個執行緒 $T_i$ 實際來借資源 (Request) 時 ：
    - Step 1：檢查 Request <= Need (確保它沒有要求超過當初宣告的最大值)
    - Step 2：檢查 Request <= Available (確保系統現在有足夠資源給它) 。
    - Step 3 (最重要)：系統會「假裝 (Pretend)」把資源分配給它，並更新矩陣狀態：Available = Available - Request   
    Allocation = Allocation + Request  
     Need = Need - Request 
    -   Step 4：對這個「假裝分配後」的新狀態跑一次前面的安全性演算法。如果安全，就真的把資源給它；如果不安全，就撤銷剛才的假裝分配，叫這個執行緒乖乖去排隊等待 。
    ## 死結偵測 (Deadlock Detection)
    如果系統放任死結發生，就需要有演算法來定期檢查系統狀態，並在發現死結時啟動恢復機制
    - 單一實例 (Single Instance) —— 等待圖 (Wait-for graph)：
        - 這是資源分配圖的簡化版，圖中的節點只有進程 (把資源節點拿掉了)。如果進程 $T_i$ 正在等待進程 $T_j$ 釋放資源，就會有一條 $T_i \rightarrow T_j$ 的邊 
        -  判斷標準：只要圖中出現循環 (Cycle)，就代表發生死結 。偵測複雜度為 $O(n^2)$
    - 多重實例 (Multiple Instances) —— 偵測演算法：
        - 類似銀行家演算法，但我們關注的是現在的請求，而不是未來的最大需求。使用三個矩陣：Available、Allocation、Request
        - 系統會尋找能夠用目前 Available 資源滿足其 Request 的進程，然後「假設」它能順利完成並釋放 Allocation 的資源 。
        - 如果一輪檢查下來，還有進程標記為未完成 (Finish[i] == false)，這些進程就是陷入死結了 。複雜度較高，為 $O(m \times n^2)$ 。
    - 考點
        - 什麼時候該執行偵測演算法？
取決於「死結發生頻率」與「一旦死結要回溯多少進程」 。如果太久才偵測一次，圖中可能會有超多個死結循環混在一起，導致系統根本查不出誰才是造成死結的「最初元兇」
## 從死結中恢復 (Recovery from Deadlock)
抓出死結後，系統必須自救，通常有兩條路可走：
- 方法一：終止進程 (Process Termination)
    - 暴力法：直接把所有捲入死結的進程全部砍掉  (代價太高，前面的運算都白費了)
    - 溫和法：一次只砍一個進程，砍完再跑一次偵測演算法，直到死結循環被打破為止
    - 要先砍誰？ 考量的指標包含：進程優先級、已經算了多久、還差多久算完、佔用了多少資源、是互動式進程還是批次進程等
- 方法二：資源搶佔 (Resource Preemption)
    - 不殺進程，而是強行把資源從某個進程手中搶過來給別人用
    - 這會面臨三個大問題：
        1. 選擇受害者 (Selecting a victim)：怎麼搶才最划算（成本最小）
        2. 回溯 (Rollback)：被搶資源的進程不能繼續跑了，必須退回到某個「安全狀態」重新開始
        3. 飢餓 (Starvation) ⚠️ (極常考)：如果系統覺得某個進程「最好欺負」，每次發生死結都去搶它的資源，它將永遠無法完成任務 。**解法是**：把「被回溯的次數」也算進成本裡，被欺負太多次的人下次就不會再被選中 。
## 多執行緒下的特殊情況：死結 (Deadlock) vs. 活結 (Livelock)
- 死結 (Deadlock)：所有執行緒都被「阻塞 (Blocked)」在那裡乾等，什麼事都不能做 。
- 活結 (Livelock)：執行緒沒有被阻塞，它為了避免死結（例如使用 pthread_mutex_trylock() 發現鎖拿不到就先退讓），不斷重複嘗試某個動作，但卻一直失敗、無法推進進度
