# 虛擬記憶體
## 虛擬記憶體的背景 
- 程式執行的基本要求是程式碼必須在記憶體中，這會限制程式的大小不能超過實體記憶體的容量
- 實際上，整個程式通常不需要同時存在於記憶體中，例如錯誤代碼、罕用功能或大型資料結構。
- 虛擬記憶體將使用者的邏輯記憶體與實體記憶體分開，允許邏輯位址空間遠大於實體位址空間。
- 這種機制讓程式不再受限於實體記憶體的大小，並允許不同行程共享位址空間、提升行程建立的效率，同時減少載入或置換所需的 I/O 操作。
- 虛擬記憶體主要可以透過「需求分頁 (Demand Paging)」或「需求分段 (Demand Segmentation)」來實作。
## 需求分頁 (Demand Paging)
- 需求分頁的核心概念是：只有在需要某個分頁時，才將其載入記憶體中。
- 這樣可以帶來許多好處，包含減少 I/O 操作、減少記憶體需求、加快回應速度並容納更多使用者同時使用。
- 專門處理分頁的置換程式 (Swapper) 被稱為 pager
- 有一種極端情況稱為「純需求分頁 (Pure demand paging)」，即行程啟動時記憶體中沒有任何分頁，直到首次存取時才觸發分頁錯誤並載入。
- 需求分頁需要特定的硬體支援：包含具備有效/無效位元的分頁表、次級記憶體 (作為置換空間)，以及指令重新啟動的功能。
- 雖然指令可能跨越多個分頁而導致多次分頁錯誤，但因為「參照局部性 (locality of reference)」的特性，實際上的效能衝擊會大幅減輕。
## 有效與無效位元 (Valid-Invalid Bit)
- 每個分頁表的條目都會關聯一個有效/無效位元，「v」代表該分頁在記憶體中，「i」代表不在記憶體中。
- 初始狀態下，所有條目的位元都會被設定為「i」
- 在位址轉換期間，如果檢查到分頁表條目為「i」，就會觸發分頁錯誤 (page fault)。
## 分頁錯誤 (Page Fault) 的處理步驟
- 首次參照到不在記憶體中的分頁時，會觸發作業系統的分頁錯誤 (trap)。
- 步驟一：作業系統會檢查表格，判斷這是一個無效參照（會直接中止程式）還是只是尚未載入記憶體。
- 步驟二：系統會尋找一個空閒的記憶體框架 (free frame)。
- 步驟三：透過排程的磁碟操作，將缺失的分頁置換 (swap) 到該空閒框架中。
- 步驟四：重設分頁表，將有效位元設定為「v」，表示分頁已存在記憶體中。
- 步驟五：重新啟動剛才觸發分頁錯誤的指令。
- 若指令會存取多個位址並造成重疊覆寫，會需要透過微碼預先計算或使用暫存器保存舊值，來確保指令能安全地重新啟動。
## 效能評估 (Performance Issue)
- 分頁錯誤率 (p) 的範圍介於 0 到 1 之間；p=0 代表完全沒有分頁錯誤，p=1 代表每次參照都會發生錯誤。
- 有效存取時間 (EAT) 的計算公式為：(1-p) * 記憶體存取時間 + p * (分頁錯誤的額外負擔 + 寫出分頁的時間 + 讀入分頁的時間 + 重啟指令的時間)。
- 分頁錯誤對效能的影響非常巨大，即使每 1,000 次存取中只有 1 次分頁錯誤，也可能導致整體運行速度變慢 40 倍。
- 為了讓系統的效能下降幅度維持在 10% 以內，分頁錯誤率必須極低（例如每 400,000 次記憶體存取中，只能發生不到 1 次的分頁錯誤）。
## 指令重新啟動 (Instruction Restart)
- **核心挑戰與情境**:
    - 必須考慮某些會同時存取多個不同記憶體位置的指令 ，例如：區塊搬移 (Block move) 或自動遞增/遞減位置 (Auto increment/decrement location)
    - 當這類指令執行到一半被分頁錯誤中斷時，是否能直接「重新啟動整個操作」會面臨困難
    - 特別是當來源端 (Source) 與目的端 (Destination) 的記憶體範圍發生重疊 (Overlap) 時 ，若盲目重新執行指令，可能會因為部分來源資料在先前已被新資料覆蓋，進而讀取到錯誤的數值
- **兩種解決方案 (Two solutions)**:
    - **微碼預先計算**: 利用微碼預先計算兩個區塊的兩端邊界，在指令真正開始搬移或修改前，先確認整個範圍內是否會發生分頁錯誤 。
    - **臨時暫存器**: 使用額外的臨時暫存器來保存被修改或覆蓋前的舊數值 ，一旦發生分頁錯誤，可以利用這些暫存器將狀態回復（Rollback）到指令執行前，以確保重新啟動時的正確性。 
## 寫入時複製 (Copy-on-Write, COW) 【常考重點】
- 寫入時複製機制允許父行程 (parent) 與子行程 (child) 在初期共用記憶體中完全相同的一組分頁。
- 只有當其中一個行程去修改了這個共用的分頁時，系統才會真正進行該分頁的複製動作。
- 這項技術讓行程的建立變得更有效率，因為系統只需要複製那些被修改過的分頁。
- 系統中通常會有一個「需求時填零 (zero-fill-on-demand)」的分頁池，空閒的分頁就是從這裡分配出來的。
## 分頁替換 (Page Replacement) 基礎與運作 【常考重點】
- 隨著行程運作，記憶體會被行程的分頁、作業系統核心以及 I/O 緩衝區等耗盡。
- 分頁替換的目的是在記憶體中找出「不是真正在使用」的分頁，並將它置換出記憶體。
- 替換演算法的終極效能目標，是希望能達到最低的分頁錯誤次數 (minimum number of page faults)。
- 分頁替換機制徹底完成了邏輯記憶體與實體記憶體之間的分離，讓較小的實體記憶體能支援龐大的虛擬記憶體。
- 系統會使用一個「修改位元 (modify / dirty bit)」，藉此降低分頁傳輸的額外負擔，也就是說只有被修改過的分頁才需要被寫回磁碟。（此為常考細節）
- 分頁替換的四大操作步驟:
    1. 找出所需分頁在磁碟上的位置。
    2. 找出空閒框架：如果有就直接用；如果沒有，就用替換演算法選出一個「犧牲者框架 (victim frame)」。若這個犧牲者分頁是髒的 (dirty)，則先將其寫回磁碟。
    3. 把所需的分頁讀入這個新空出的框架中，並更新分頁表與框架表。
    4. 重新啟動剛才觸發中斷的指令。
- 因為一次分頁錯誤可能包含把舊分頁寫出以及把新分頁讀入，潛在需要 2 次分頁傳輸，這會增加有效存取時間 (EAT)。
## 演算法評估與框架關係
- 系統需要「框架配置演算法 (Frame-allocation algorithm)」來決定給每個行程多少框架、以及替換哪裡；同時也需要「分頁替換演算法 (Page-replacement algorithm)」來確保最低的分頁錯誤率。
- 評估演算法效能的方式是透過餵給它一段「參考字串 (reference string)」，然後計算會發生多少次分頁錯誤。

## FIFO 演算法與 Belady 異常【極常考】
- 先進先出 (First-In-First-Out, FIFO) 是一種根據進入記憶體時間順序來替換的分頁演算法。
- **Belady 異常 (Belady's Anomaly)**: 
這是一個違反直覺且極常被考出來的現象，意思是「當給予系統更多的分頁框架時，反而導致產生更多的分頁錯誤！
- 講義中的範例展示，在使用特定的參考字串 (如 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5) 時，擁有 4 個框架所產生的分頁錯誤次數，竟然高於只有 3 個框架的狀況。
## 最佳分頁替換演算法 (Optimal Algorithm, OPT)【常考概念】
- **核心精神**: 替換掉「在未來最長一段時間內不會被使用到」的分頁。
- **特性**: 它能產生最低的分頁錯誤率 。OPT 屬於堆疊演算法 (stack algorithm)，不會發生 Belady 異常 (Belady's Anomaly) 。
- **盲點**: 因為作業系統無法預知未來的分頁存取順序，所以在現實中是不可能實作出來的 。
- **用途**: 主要用來作為效能測量的基準，衡量其他演算法的表現有多接近完美 。
## 近期最少使用演算法 (Least Recently Used, LRU)【極常考】
- **核心精神**: 利用過去的經驗來預測未來，替換掉「已經最久沒有被使用」的分頁 。
- **特性**: 通常效能表現良好，且經常被實際採用 。與 OPT 一樣，LRU 也不會發生 Belady 異常 。
- **硬體實作挑戰**: 純 LRU 需要特殊的硬體支援且執行速度較慢 。常見有兩種實作方式：
    - **計數器 (Counter)**: 為每個分頁條目配備計數器，每次參照時複製時鐘數值。發生替換時，需要「搜尋」整張表找出最小值 。
    - **堆疊 (Stack)**: 使用雙向鏈結形式保存分頁號碼。被參照到的分頁移到堆疊最頂端，替換時直接抓最底端的分頁，省去搜尋的時間，但每次更新指標的成本較高 。
## LRU 近似演算法 (LRU Approximation)【常考重點】
- **核心精神**: 因為純 LRU 實作成本太高，所以改用硬體提供的「參照位元 (Reference bit，初始為 0)」來近似評估分頁的使用頻率 。
- **第二次機會演算法 (Second-chance / Clock algorithm)：**
    - 結合 FIFO 的概念與參照位元 。
    - 如果輪到的分頁參照位元是 0，代表最近沒用過，直接替換掉 。
    - 如果參照位元是 1，則給它「第二次機會」：將位元清為 0、把分頁留在記憶體中，然後指標繼續往下尋找下一個犧牲者 。
- **增強型第二次機會演算法 (Enhanced second-chance)：**
    - 同時考量「參照位元 (R)」與「修改 / 髒位元 (M)」 。
    - 共分為四種等級，替換優先順序由最適合 (1) 到最不適合 (4)：
        1. (0,0)：最近沒用過，也沒修改過（最佳犧牲者，不需要寫回磁碟） 。
        2. (0,1)：最近沒用過，但被修改過（踢出去前需要花時間寫回磁碟） 。
        3. (1,0)：最近有用過，但沒修改過 。
        4. (1,1)：最近有用過，且被修改過 。
## 計數演算法 (Counting Algorithms)
- **核心精神**: 記錄每個分頁被參照的總次數，但在作業系統中並不常見 。
- **LFU (最不常使用)**: 替換掉參照計數「最小」的分頁 。
- **MFU (最常使用)**: 基於「計數最小的分頁可能是剛被載入進來，尚未被充分使用」的論點，反而替換掉參照計數「最大」的分頁 。
## 分頁緩衝演算法 (Page-buffering algorithms)
- **核心精神**: 系統會隨時保留一個「空閒框架池 (pool of free frames)」 。
- **加速機制**: 當發生分頁錯誤時，不需要等待犧牲者分頁寫回磁碟，可以直接把需要的新分頁先讀入空閒框架池中，讓程式提早恢復執行 。
- **批次處理**: 系統可能還會維護一個「已修改分頁清單 (modified frame list)」，趁備份儲存裝置 (backing store) 空閒時，把這些分頁寫回磁碟並將修改位元重設為非髒狀態 。
- **亡羊補牢**: 被選為犧牲者但內容還完好留在空閒池的分頁，若在框架被覆蓋前再次被程式參照，可以直接重新利用，免去從磁碟重新載入的懲罰 。
## 應用程式與分頁替換的衝突
- **問題點**: 所有的演算法都是作業系統在「猜測」未來的存取模式 。對於資料庫或資料倉儲等具有特殊存取模式的應用程式，透過作業系統的虛擬記憶體進行緩衝反而會讓效能更差（例如在資料倉儲中，MFU 表現通常優於 LRU） 。
- **解法**: 部分作業系統給予特殊程式權限使用「裸磁碟 (Raw disk) / 裸 I/O (Raw I/O)」 。這允許應用程式將儲存分區視為大型的循序邏輯區塊陣列，直接略過作業系統的檔案系統與分頁緩衝結構，由程式自己管理記憶體 。
## 框架配置 (Allocation of Frames)
行程需要最低數量的框架才能執行，而最大數量則取決於系統中的總框架數 。作業系統分配框架的策略主要有以下幾種：
- **固定配置 (Fixed allocation)**:
    - **平均配置 (Equal allocation)**: 不看行程大小，直接將記憶體平均分配給所有行程 。
    - **比例配置 (Proportional allocation)**: 依照行程的邏輯記憶體大小比例來分配框架 。
- **優先權配置 (Priority allocation)**:
    - 不單看大小，而是根據行程的優先權來配置 。
    - 當發生分頁錯誤時，行程可以選擇替換自己的框架，或是從「優先權較低」的行程手中奪取框架 。
- **全域替換 vs. 區域替換 (Global vs. Local Allocation)：**
    - **全域替換 (Global)**: 行程可以從系統所有的框架中挑選犧牲者（包含搶走別人的分頁） 。這種方式能獲得較佳的系統吞吐量，因此較為常見，但缺點是單行程的執行時間會不穩定 。
    - **區域替換 (Local)**: 行程只能從自己分配到的專屬框架中進行替換 。優點是每個行程的效能較為一致，但缺點是可能會造成記憶體未被充分利用 。
## 輾轉現象 (Thrashing)【極常考】
- **定義**: 如果一個行程沒有分配到「足夠」的分頁框架，會導致分頁錯誤率極高 。這會讓行程把時間全部花在把分頁換入與換出磁碟上，這種現象就稱為「輾轉現象 (Thrashing)」 。
- **引發系統崩潰的連鎖效應**: 
    1. Thrashing 發生時，因為都在等待 I/O，CPU 使用率會大幅降落 。
    2. 作業系統看到 CPU 太閒，誤以為系統負載不足，於是提高「多道程式設計的程度 (degree of multiprogramming)」，把更多新的行程丟進系統執行 。
    3. 新行程需要更多記憶體，導致大家搶奪更少的分頁，Thrashing 更加惡化，最終系統效能徹底崩潰（可參考第 49 頁的圖表曲線） 。
- **根本原因**: 需求分頁能順利運作是基於行程的「局部性模型 (Locality model)」 。當系統中所有行程的「局部性大小總和」大於「實體記憶體總容量」時，Thrashing 就必然會發生 。
- **區域控制**: 可以透過強制使用「區域或優先權分頁替換」來限制 Thrashing，避免一個行程出包拖垮全系統 。
## 工作集模型 (Working-Set Model)【常考重點】
為了避免 Thrashing，作業系統需要一種方法來預測行程到底需要多少記憶體。
- **核心概念**: 用來近似評估行程的局部性 。定義一個工作集視窗 $\Delta$（例如：最近的 10,000 次分頁參考） 。  
- 工作集大小 ($WSS_i$)：代表行程在最近 $\Delta$ 時間內，實際參照到的不重複分頁總數 。
- **防止 Thrashing 的策略：**
    - 計算系統總需求 $D = \sum WSS_i$ 
    - 如果總需求大於總實體記憶體 ($D > m$)，系統即將發生 Thrashing 。 
    - 處置方式：作業系統會強制暫停 (suspend) 其中一個行程，釋放它的記憶體給其他行程使用 。
- **實作追蹤**: 系統會利用間隔計時器 (interval timer) 搭配參照位元 (reference bit) 來近似追蹤工作集 。當計時器觸發中斷時，複製並將參照位元歸零；若記憶體中某個分頁的位元為 1，則判定它屬於工作集 。
## 分頁錯誤頻率機制 (Page-Fault Frequency Scheme)
除了工作集模型外，這是另一種更直觀預防 Thrashing 的方法：直接控制分頁錯誤率 。
- **運作原理**: 作業系統會為分頁錯誤率設定一個「可接受的上限與下限」 。
- **動態調整：**
    - 如果行程的實際錯誤率太高（超過上限），代表它快撐不住了，系統會增加分配給它的框架數量 。
    - 如果行程的實際錯誤率太低（低於下限），代表它記憶體多到用不完，系統會減少（回收）它的框架，拿去借給別人 。
## 預先分頁 (Prepaging)
- **目的**: 為了解決行程剛啟動時，因為記憶體空空如也而產生的大量分頁錯誤 。
- **機制**: 在分頁被真正參照到之前，作業系統就先猜測並把部分或全部可能用到的分頁預先載入記憶體中 。
- **效能權衡**: 這是一場賭博。如果預先載入的分頁最終沒被用到，反而會浪費寶貴的 I/O 傳輸與記憶體空間 。系統必須評估「省下分頁錯誤所獲得的效益」是否大於「載入無用分頁的成本」 。
## 分頁大小 (Page Size)
- **設計考量**: 作業系統（或客製化 CPU）在決定分頁大小時，需要權衡非常多因素。包含：內部碎裂程度、分頁表大小、I/O 傳輸時間、總 I/O 量、分頁錯誤次數、局部性 (Locality) 以及 TLB 的大小與效率等 。
- **發展趨勢**: 分頁大小通常設定為 2 的次方（如 4KB 到 4MB），且隨著硬體與記憶體容量的進步，平均的分頁大小有逐漸增長的趨勢 。
## TLB 涵蓋範圍 (TLB Reach)【常考觀念】
- **定義**TLB (Translation Look-aside Buffer) 所能涵蓋的實體記憶體範圍，公式為：TLB 涵蓋範圍 = (TLB 大小) × (分頁大小) 。
- **理想狀態**: 行程的「工作集 (Working Set)」最好能完全裝進 TLB 的涵蓋範圍內，否則會引發極高的分頁錯誤率 。
- **擴大涵蓋範圍的方法：**:
    1. **增加分頁大小**: 雖然能擴大範圍，但缺點是可能讓不需要那麼大空間的程式產生更多內部碎裂 。
    2. **提供多種分頁大小**: 這是一種兩全其美的作法，讓需要大分頁的應用程式有機會使用，同時又不會增加整體系統的碎裂問題 。
## 程式結構對效能的影響 (Program Structure)【極常考：陣列走訪】
這頁展示了程式設計師的寫法，會如何嚴重影響虛擬記憶體的效能。假設有一個 $128 \times 128$ 的二維陣列，且每一列 (Row) 剛好佔用一個分頁 。
- **效能極差的寫法（Program 1）**:外迴圈走欄 (j)，內迴圈走列 (i) 。
    - 因為 C/C++ 陣列在記憶體中是「以列為主 (Row-major)」連續存放的，這種寫法會讓程式不斷在不同的分頁間跳躍，導致產生 $128 \times 128 = 16,384$ 次分頁錯誤 。
- **效能極佳的寫法（Program 2）**:外迴圈走列 (i)，內迴圈走欄 (j)。
    - 這種寫法順著實體記憶體的連續位址存取（善用空間局部性），只需 128 次分頁錯誤就能處理完畢 。
## I/O 互鎖 / 鎖定 (I/O Interlock)
- **機制**: 有時候，某些特定的分頁必須被強制「鎖定 (Locked)」在記憶體中，不允許被分頁替換演算法踢出去 。
- **原因**: 當這些分頁正在作為外部設備的 I/O 緩衝區（例如正在將檔案複製進來或寫出去）時，如果中途被 OS 置換出記憶體，正在進行的 I/O 操作就會寫入到錯誤的地方，導致資料損毀 。
## 非均勻記憶體存取 (Non-Uniform Memory Access, NUMA)
- **背景**: 以往的記憶體模型假設 CPU 存取任何記憶體位置的速度都是一樣的 。但在 NUMA 架構（如多個系統板互連）中，存取速度會因為 CPU 與記憶體之間的「物理距離」而有所不同 。
- **最佳化策略**:作業系統排程器應該盡量將記憶體配置在「靠近」執行該執行緒的 CPU 所在的系統板上 。
- **實作範例**: Solaris 作業系統透過建立「局部性群組 (lgroups)」來解決。系統會盡量在執行緒的所屬群組 (home lgroup) 中分配資源，若真的不夠，才會向外跨群組尋求資源 。
## 記憶體壓縮 (Memory Compression)
當系統記憶體不足時，除了前面學到的「將分頁置換 (Swapping) 到磁碟」之外，另一種替代方案就是「記憶體壓縮」。
- **運作機制**: 系統會挑選幾個被修改過的框架（例如第 68 頁例子中的 15, 3, 35），將它們的資料「壓縮」後，全部塞進單一個空閒框架（如框架 7）中，然後把這個框架放入「已壓縮框架清單 (compressed frame list)」裡 。這樣做可以在不使用磁碟置換的情況下減少記憶體的使用量 。
- **應用場景**: 這點非常重要！行動裝置系統 (Mobile systems) 通常不支援標準的置換機制 。因此，記憶體壓縮成為了大多數行動作業系統（如 iOS, Android）不可或缺的記憶體管理策略 。
## 核心記憶體配置 (Allocating Kernel Memory)【極常考重點】
作業系統核心 (Kernel) 對待記憶體的方式與一般使用者程式不同，通常會從一個專屬的空閒記憶體池來配置 。核心必須非常保守地使用記憶體，並盡可能將「碎裂 (fragmentation)」降到最低 。此外，某些核心記憶體（例如為了硬體裝置的 I/O）必須是實體連續 (physically contiguous) 的 。  
為了解決核心記憶體的配置需求，主要有兩種經典的演算法：
1. **夥伴系統 (Buddy System)**
    - **運作機制**: 從一段大小固定且「實體連續」的記憶體段落開始分配 。它使用「2 的次方 (power-of-2) 配置器」
    - **配置規則**: 它會把核心的記憶體請求，無條件進位到下一個 2 的次方大小 。如果目前可用的空閒區塊比需要的大，就會把區塊「對半切（分裂成兩個較小的 buddy）」，一直切到尺寸剛好符合為止 。（例如：要 21KB，會進位到 32KB；若目前只有 256KB 的區塊，就會一路切成 128KB、64KB、最後切出 32KB 來配給它 ）。
    - **優缺點**:
        - **優點**:當記憶體釋放時，相鄰且未使用的夥伴可以「非常快速地合併 (coalesce)」成一個大區塊 。
        - **缺點**: 會造成碎裂 (fragmentation) 。確切地說，這叫「內部碎裂 (Internal fragmentation)」，因為你明明只要 21KB，系統卻硬塞給你 32KB，中間浪費了 11KB。
2. **Slab 配置 (Slab Allocation)**  
為了解決 Buddy System 容易浪費空間的問題，發展出了 Slab 機制。
- **名詞定義**:
    - Slab：由一個或多個「實體連續的分頁」所組成 。  
    - Cache (快取)：由一個或多個 Slab 所組成 。
- **運作機制**: 核心中「每一種獨特的資料結構（例如 process descriptor、file object）」，系統都會為它建立一個單一專屬的 Cache 。當 Cache 被建立時，系統會預先在裡面塞滿該資料結構的實例，稱為「物件 (objects)」，並標記為 free 。當核心需要儲存資料時，直接拿一個 free 的物件來用，並標記為 used 。
- **優缺點**:
    - **優點 1：沒有碎裂 (no fragmentation)**: 因為每個 Cache 裡的格子大小就是專門為該資料結構量身打造的，完全不會浪費空間。
    - **優點 2：快速滿足記憶體請求 (fast memory request satisfaction)**: 因為物件都已經預先建構好了，核心要用的時候「隨拿隨用」，不需要臨時去切記憶體。
